# Phase 0 notes

Failures seen only on PostgreSQL while porting tests (task 0.1), and the minimum fix applied.

| #   | Symptom                                                          | Cause                                                                                                        | Fix                                                      |
| --- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| 1   | `syntax error at or near "RETURNING"` in `invoices.spec.ts`      | Test insert helpers ended SQL with `;`; the PG adapter appends ` RETURNING id` after it                      | Removed the trailing `;` in the test helpers (test-only) |
| 2   | `addInvoice` → `error.sqlSyntaxError` for invoices with no items | `getInvoices` built `"parentInvoiceItemId" IN ()` from an empty list; SQLite accepts it, PostgreSQL does not | Skip the snapshot query when the id list is empty        |

3. **Stale unique constraint (legacy PG bug).** Migration 22 adds `invoices_businessId_invoiceFullNumber_clientId_key` unquoted (PG stores it lower-case); migration 24 drops the quoted camel-case name, so the old 3-column constraint survived next to the new 4-column one and a quotation → invoice conversion hit `duplicate key`. Fix: migration 24 also drops the unquoted name. The 0.2 baseline must contain only the 4-column constraint.
4. **`nextSequence` is `BIGINT`**, which `pg` returns as a string. Services already wrap it in `Number()`; only the test's raw read was changed.
5. **Silent legacy migration failures.** Legacy `up()` functions catch errors and return `{ success:false }`, which the old runner ignored. `pgTestDb` now throws on that; all 30 migrations apply cleanly on PG.
6. **Migration 28 is not re-runnable after 29** (its backfill reads `invoice_customizations."layout"`, dropped by 29). The layouts spec now builds the DB with `stopBefore: '20260902-28'`, then runs 28 twice and asserts neither run fails, as the original SQLite test did.

## Decisions

- **S7 tax columns (user, 2026-09-15):** review S7 drops legacy invoice `taxName/taxRate/taxType` and item `taxRate/taxType` "from the baseline", but Phase 0 must not change invoice behaviour. Ruling: `0001-baseline.sql` keeps these columns (`INTENTIONAL_DROPS` stays empty in Phase 0); Phase 2 drops them with a forward migration when the GST tax module replaces them.

## Task 0.2 deviations

- `0001-baseline.sql` = `pg_dump --schema-only` + `--data-only --column-inserts` of the legacy schema on PG 17, with `SET`/`\restrict`/comments/`public.` stripped, no-op `setval`s removed, seed `createdAt/updatedAt` set to `now()`, and the legacy `migrations` table removed (the SQL runner owns it). Seeds: categories 2, currencies 10, layouts 6, settings 1, units 13 (no template rows exist).
- New `runSqlMigrations(connectionString, dir)` in `migrationRunner.ts` uses `pg` directly (the adapter rewrites every `?` to `$n`, which would corrupt SQL text). The legacy `runMigrations` stays until 0.3.
- `setup.ts` is trimmed, not deleted: `initSchema`/`initInitialData`/`openSqlLite` are gone, but `testPostgresConnection`/`openPostgreSql` stay until 0.4 deletes their web callers, so `tsc -p tsconfig.webserver.json` keeps passing. Web `setupDB` now runs the SQL migrations and rejects SQLite.
- Known breakage until later tasks: Electron `src/backend/main/database.ts` (removed in 0.5); CI `npm run test` needs a PostgreSQL service (0.6); `tsc` does not copy `.sql` files into `dist-be`, so the Docker image must ship `src/backend/shared/migrations/*.sql` (0.6); `.github/copilot-instructions.md` still describes legacy migrations (0.5 docs pass).
- `layouts.migration.spec.ts` now asserts the baseline layout seeds.

## Task 0.3 deviations

- **Booleans converted to real `BOOLEAN` in the baseline.** All 30 `INTEGER ... CHECK (col IN (0,1))` columns named in `BOOLEAN_FIELDS` (`isArchived`, `isDarkMode`, `showQuantity`, …, 8 tables + `settings`) are now `boolean DEFAULT true/false NOT NULL`, with the 0/1 check constraints dropped. `0001-baseline.sql` was rebuilt by applying the committed baseline to a scratch DB, running the column conversion, and re-dumping — not by hand-editing SQL. `boolToInt`/`convertBooleanFields(Array)`/`convertBooleanFieldsToInt(Array)` are deleted; `pg` now returns real JS booleans and services pass them straight through.
- **`Db` type (`shared/db/tx.ts`)** has only `{ get, all, run, query }` (no `type`/`close`) and is obtainable only via `withTx`/`createWithTx(pool)`; a `Db` used after its transaction ends throws `DbUsedOutsideTransaction` (covered by `db/__tests__/tx.spec.ts`, including a rollback-on-throw test). `shared/db/client.ts` and `shared/types/DatabaseAdapter.ts` are deleted.
- **`filterFunctions.ts` rewritten to parameterize every filter value** (client/business name, status, date range), not just the two spots the task named in `invoices.ts` `getInvoices`. The old code built these clauses with manual `'` -escaping (`value.replace(/'/g, "''")`), which CLAUDE.md's "no string-interpolated SQL values" rule forbids; since this file was already being rewritten to drop `db.type`, fixing it was the smallest-scope moment to do it. `getWhereClauseFromFilters`/`getHavingClauseFromFilters` now return `{ sql, params }`; callers (`entitiesFunctions.ts`, `invoices.ts`, `items.ts`, `presets.ts`) merge `params` into their query params.
- **Pulled forward from 0.4 (unavoidable):** deleting `client.ts` breaks everything downstream of the old `dbInstance` singleton (`webserver/database.ts`, `webserver/migration.ts`, `webserver/controllers/database.ts`, and all 13 controllers' `dbInstance!`/`requireDB` use) — there's no way to land 0.3 without also retiring that pattern. Deleted those 3 files; every controller now does `withTx(db => service(db, …))` per route, `requireDB`/`listDbLimiter` removed from `webserver/utils/functions.ts`, `main.ts` no longer mounts the DB-picker routes. This is exactly 0.4's "replace `dbInstance!` with `withTx`" item, done early — 0.4 still owns CORS/body-limits/helmet/error-handler/`migrate.ts`.
- **`invoices.ts` correctness fixes made while removing its own transaction management** (kept narrow, per CLAUDE.md's invoices.ts rule):
  - `addInvoice`/`updateInvoice` ran the sequence-table update _after_ the (now-removed) `COMMIT`; moved before the final read/return so it's part of the one ambient transaction, per the task's explicit instruction.
  - `duplicateInvoice`'s quotation→invoice path wrote `status='closed'` on the original invoice _before_ validating the new invoice number; reordered to validate first (the write no longer needs its own `ROLLBACK`, which the task removes anyway).
  - Two pre-existing bugs fixed in passing, found while re-reading these functions: `addInvoice`/`updateInvoice`'s sequence-failure branch returned `{ key: result.key }` (the _invoice_ handler's already-successful result) instead of `resultSequence.key`.
  - `getInvoices`'s 10-way `Promise.all` fan-out is now sequential — a single `withTx` connection can only run one query at a time; running it concurrently was silently serialized by `pg` with a deprecation warning, not a real bug on the old per-call-pool-checkout adapter but unsafe on the new one-connection-per-transaction model.
- **Deferred to 0.5 as planned:** `shared/enums/databaseType.ts`, `dbInitType.ts`, `types/postgresConfig.ts`, `types/sqliteConfig.ts` are now unused outside Electron `main/*` (already broken since 0.2) but are left in place; 0.5's file-deletion list already covers them.
- **`MIGRATION_DATABASE_URL` fallback** (task 0.3 line: "using `MIGRATION_DATABASE_URL`, falls back to `DATABASE_URL` in dev") isn't wired yet — `runSqlMigrations(connectionString, dir)` takes an explicit connection string; nothing in 0.3 calls it in production (the old caller was deleted, the new one is 0.4's `webserver/migrate.ts`). That script must resolve `MIGRATION_DATABASE_URL ?? DATABASE_URL` itself.

## Test infrastructure

- `pgTestDb` now runs `0001-baseline.sql` via `runSqlMigrations` (not legacy `.ts` migrations) and exposes `withTx` (bound to a scratch-database pool) instead of a raw `Db` — a `Db` only exists inside a transaction, so every test helper/assertion wraps its own `testDb.withTx(db => …)` call, one per logical operation (mirrors "one request = one transaction" in production).
- `layouts.migration.spec.ts` no longer re-runs the layouts table migration (not re-runnable: `ADD COLUMN`); it asserts the migrated state and re-runs the seed twice for idempotency.
- Local install: `npm ci --ignore-scripts && npm rebuild sqlite3 esbuild` (the `postinstall` Electron rebuild breaks `sqlite3` under Node; removed in 0.5).
- Local dev: `DATABASE_URL` must be set by hand when running `npm run dev:webserver` until 0.6 adds `.env`/Docker wiring.

## Task 0.4 deviations

- **Controllers were already done in 0.3** (see above); 0.4 landed only the `main.ts` wiring, `migrate.ts` and the dependency changes.
- **15 MB parser is mounted per route prefix, write methods only.** `LARGE_BODY_ROUTES` (`/api/invoices`, `/api/businesses`, `/api/presets`, `/api/styleProfiles`) each get a `express.json({ limit: '15mb' })` guard that defers to `next()` for non-`POST/PUT/PATCH`; the global `express.json({ limit: '1mb' })` runs after and body-parser skips a request whose body is already parsed. Prefix mounting also covers the sub-routes (`/api/invoices/duplicate`, `/api/presets/batch`, …).
- **Error keys reuse existing i18n strings** rather than adding new ones to all 5 locales: `entity.too.large` → `error.fileTooLarge`, `entity.parse.failed` → `error.invalidFile`, everything else → `error.unknownError`. 5xx responses send a fixed `Internal server error` message (no stack, no upstream text); the log line is `[requestId] METHOD path status key: message` with no request body.
- **`requestId` lives on `res.locals`**, not a `Request` augmentation, so no `.d.ts` module augmentation is needed for `tsconfig.webserver.json`.
- **`cors` and `@types/cors` removed from `package.json`; `helmet` added.** 0.5's dependency list did not name `cors`, but nothing imports it once `main.ts` drops the middleware.
- **`webserver/config.ts` trimmed** to `DEV_SERVER_URL`/`PORT`/`VERSION`; `FE_SERVER_URL` was only used by CORS and `DB_DIRECTORY` was a SQLite leftover.
- **ESLint:** added `@typescript-eslint/no-unused-vars` with `argsIgnorePattern: '^_'` — Express detects an error handler by `fn.length === 4`, so the unused `_next` parameter has to stay. This made 4 `eslint-disable-next-line` directives in `renderer/shared/api/platformApi.ts` redundant; they were removed by `eslint --fix`.
- **`migrate.ts`** resolves `MIGRATION_DATABASE_URL ?? DATABASE_URL` (the fallback 0.3 deferred) and `path.resolve(__dirname, '../shared/migrations')`. It is re-runnable (`No new migrations to apply` on the second run).
- **Environment conflict found while running the 0.4 check:** host port 5432 is held by an unrelated `i-ticket-postgres-1` container, so `invoice-expense-postgres-1` came up unpublished and `localhost:5432` authenticates against the other project's database. The smoke test was run against a scratch `invoice_expense` database on the test instance (`localhost:5433`) instead. Nothing in the repo was changed for this; free port 5432 (or remap it in `docker-compose.dev.yml`) before using the dev database.

## Task 0.5 deviations

- **Deleted beyond the task's list, all orphaned by it:** `src/renderer/shared/hooks/dbSelector/` (5 hooks calling the deleted `/api/databases*` routes), `shared/utils/receiptFunctions.ts` (only `usePrintReceipt` used it), `shared/types/dbSelector.ts`, `types/postgresConfig.ts`, `types/updater.ts`, `renderer/shared/enums/dbInitType.ts`, and `data/` (the SQLite file directory). `shared/types/global.d.ts` was deleted whole — it declared nothing but `window.electronAPI`.
- **Sidebar "logout" removed.** It meant "go back to the database chooser": it dispatched `logout()`, which set `dbReady = false`. With no chooser there is nothing to log out to, so the menu item, its confirmation and the `logout` reducer are gone. **Phase 1 adds a real logout with authentication.** `dbReady`, `newVersion` and `updateMessage` left `PageState` with their reducers and selectors.
- **Receipt printing UI removed, not the setting.** `settings.receiptPrintingOn` stays in the baseline and in both `Settings` types; only the toggle in the settings menu, the `MoreActionDropdown` item, the preview FAB and `setReceiptPrintingOn` are gone. `MenuItemSettings.Receipt` stays — despite the name it selects the _Customize invoice_ panel, not anything receipt-related.
- **Dev-mode CORS replacement (necessary, not in the task list).** 0.4 removed CORS on the premise of same-origin serving, but in dev the SPA is on `:5173` and the API on `:3000`. `vite.config.ts` now proxies `/api/*` to `API_PROXY_TARGET ?? http://127.0.0.1:3000`, so the browser only ever talks to the Vite origin; `playwright.config.ts` sets `API_PROXY_TARGET` instead of `VITE_API_URL`. Without this the app renders but every request fails — the e2e spec caught it. `VITE_API_URL` still works for split-origin deployments.
- **`vite.config.ts` `base` changed from `./` to `/`.** The relative base existed for Electron's `file://` loading; with `createBrowserRouter` and deep URLs a relative base resolves assets against the current path.
- **Four pre-existing type errors fixed**, because `npm run typecheck` is a 0.5 exit criterion and `tsconfig.app.json` covers all of `src`:
  - `invoices.ts` `processItems`/`processAttachments` took a `Db` they never used (the handlers close over it); the parameter and its 4 call-site arguments are gone. No behaviour change.
  - `createPdfBlob` never passed `layoutRequired` to `PDFDocument`, which requires it. Both export hooks now pass `t('common.layoutRequired')`, matching `PreviewCore`.
  - `platformApi`'s `addPreset`/`updatePreset` decoded only `signatureData` from the response (`mapPresetFromWeb1`) although the server base64-encodes all five binary fields, so `businessLogo`, `qrCode` and both watermarks came back as strings after a save. Both now use the full mapper, renamed `mapPresetFromWeb`; `mapPresetFromWeb1` is deleted.
- **`e2e/v2-layout.spec.ts` rewritten.** It created a SQLite database through `POST /api/databases` (deleted in 0.3) and switched to it through `localStorage`; it now seeds a layout through the API and asserts the `/layouts` page renders it. It passes, which is also the runtime proof that the SPA boots with no `DatabaseChooser` and no `dbReady` gate.
- **ESLint / scripts:** `test` is now `vitest run` (it was `vitest`, i.e. watch mode, which would hang `npm test` in CI). `dev` is `concurrently "npm:dev:react" "npm:dev:webserver"`. `typecheck` runs all three tsconfigs. `dev:react`/`dev:webserver` stay because Playwright starts them individually. All `docker:*` scripts are gone (they called the deleted `scripts/*.cjs` and `docker-compose.standalone.yml`); 0.6 owns their replacements.
- **`npm ci` no longer needs `--ignore-scripts`** now that the `postinstall` Electron rebuild and `sqlite3` are gone. The local-setup workaround recorded in the 0.2 notes is retired.
- **i18n:** 21 keys orphaned by these deletions were removed from all 5 locales (`databaseChooser.*`, the updater and receipt-printing strings, `menuItems.logout`). `common.password` was kept for Phase 1's login form. Pre-existing unused keys (`*.filter.*Desc`, the SQLite-era `error.*` entries) were left alone.
- **Docs:** README rewritten for the fork, `.github/copilot-instructions.md` rewritten to point at `CLAUDE.md`, `AGENTS.md` and the BMAD agent/prompt files de-Electron-ed. `TUTORIAL.md` and `History.md` are untouched upstream artifacts and still describe the desktop app — the README says so; a tutorial rewrite belongs with Phase 4 UX.
- **Left for 0.6 as planned:** `Dockerfile`, `docker-compose.yml`, `scripts/docker-start.sh`, `scripts/nginx.conf.template`, `.github/workflows/main.yml` (still `prettier --write`, no PostgreSQL service) and `docker-publish.yml`. The 11 files `prettier --check .` flags are all pre-existing (`CLAUDE.md`, `docs/**`, `index.html`).
